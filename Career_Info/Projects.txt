  What architecture did you choose, and why? 
  
  
  Architecture: run-centric control plane with separated execution and independent scorers.

  What we chose

  Prompt Lab (FastAPI + UI)          ← control plane: run, store, trigger, display
          │
     ┌────┴────┐
     ▼         ▼
  n8n Ask/Pulse   n8n LLM Judge     ← execution plane (agents + judge model)
     │
     ▼
  data/<agent>/runs/<runId>.json    ← durable run artifact
     │
     ▼
  Python packages                   ← schemas, packing, deterministic scores
  (eval_store, llm_judge, tool_routing_eval, manual_eval, …)

  Pattern: capture once → score many ways
  One Ask/Pulse execution becomes a run JSON; then code eval, LLM-as-judge, Recall@5 routing eval, and human notes overlay
  independently — none silently rewrite another’s overall score.

  Why

  ┌───────────────────────┬────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │ Decision              │ Why                                                                                                │
  ├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ Prompt Lab as control │ One place to run scenarios, batch CSVs, inspect traces, and trigger judges — without baking eval   │
  │ plane                 │ into the agent workflow.                                                                           │
  ├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ n8n for agent + judge │ Matches production Ask/Pulse path; judge uses Azure via n8n so Python doesn’t own LLM credentials  │
  │                       │ or prompt plumbing.                                                                                │
  ├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ Run artifact on disk  │ Replay and re-judge after the judge improves; shared truth instead of “looks good in demo.”        │
  ├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ Independent scorers   │ Narrative quality (LLM) ≠ tool allowlist math (Recall@K) ≠ human notes — they can disagree, and    │
  │                       │ that signal is useful.                                                                             │
  ├───────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ CSV goldens +         │ Product test pack stays readable; MCP/widget names can change without rewriting every case.        │
  │ mapping.json          │                                                                                                    │
  └───────────────────────┴────────────────────────────────────────────────────────────────────────────────────────────────────┘

  One line: Prompt Lab is an eval harness around durable runs — not an in-agent scorer — so agent quality can be measured and
  improved without relying on demo luck.
  
 also to prepare a good quality Golden Set
  P0 / P1 / P2 are priority tiers on Prompt Lab scenario CSVs — how important a test case is for regression, not different
  systems.

  ┌──────────┬─────────────────────────────┬──────────────────────────────────────────────────────────────────────┐
  │ Priority │ Meaning                     │ Role in eval                                                         │
  ├──────────┼─────────────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ P0       │ Must-pass product behaviors │ Primary gate — fix these first; batch runs start here                │
  ├──────────┼─────────────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ P1       │ Important coverage          │ Run after P0 is green — multi-source, decision support, richer flows │
  ├──────────┼─────────────────────────────┼──────────────────────────────────────────────────────────────────────┤
  │ P2       │ Lower priority / edge       │ Nice-to-have, coaching, sensitive peer/team cases                    │
  └──────────┴─────────────────────────────┴──────────────────────────────────────────────────────────────────────┘

  Example from the pack: “What skills do I have?” / “What’s overdue?” → P0. “Infer skills from activity” → P1. “Should
  negotiation be added to my profile?” → P2.

  Batch order is P0 → P1 → P2 so you don’t burn time on edges while core Ask is broken.
  
  
  
  and this entire system can be also used for RLHF
  
  
  Prompt Lab isn’t an RLHF trainer — it’s a data + preference factory that can feed one. The same run-centric design maps
  cleanly.

  How it plugs in

  Ask/Pulse runs (Prompt Lab)
          │
          ▼
  run JSON: prompt, narrative, tools, widgets, debugTrace, expected*
          │
     ┌────┼────────────────────────┐
     ▼    ▼                        ▼
  Human   LLM judge              Ideal / golden
  manualEval  llmJudge           idealResponse
  prefer A/B  score dimensions   target answer
          │
          ▼
  Preference / reward dataset
          │
     ┌────┴────┐
     ▼         ▼
  Reward model / DPO pairs     SFT on idealResponse
          │
          ▼
  RL / preference optimization on the policy (Ask agent / router)

  What you already have → RLHF use

  ┌─────────────────────────────────────────────────┬───────────────────────────────────────────────────────┐
  │ Prompt Lab piece                                │ RLHF role                                             │
  ├─────────────────────────────────────────────────┼───────────────────────────────────────────────────────┤
  │ Run artifacts (prompt, narrative, tools, trace) │ Offline trajectories for the policy                   │
  ├─────────────────────────────────────────────────┼───────────────────────────────────────────────────────┤
  │ manualEval (pass/partial/fail + remarks)        │ Human preference labels — strongest RLHF signal       │
  ├─────────────────────────────────────────────────┼───────────────────────────────────────────────────────┤
  │ idealResponse                                   │ SFT targets / chosen completions                      │
  ├─────────────────────────────────────────────────┼───────────────────────────────────────────────────────┤
  │ llmJudge dimensions                             │ Cheap proxy rewards (filter or rank before humans)    │
  ├─────────────────────────────────────────────────┼───────────────────────────────────────────────────────┤
  │ toolRoutingEval / Expected Tools                │ Process reward: right tools in allowlist / trajectory │
  ├─────────────────────────────────────────────────┼───────────────────────────────────────────────────────┤
  │ P0→P2 CSVs                                      │ Curated prompt distribution for sampling & eval       │
  ├─────────────────────────────────────────────────┼───────────────────────────────────────────────────────┤
  │ Batch + re-judge                                │ Refresh labels as the judge/policy improves           │
  └─────────────────────────────────────────────────┴───────────────────────────────────────────────────────┘

  Practical RLHF pipeline on this stack

  1. Collect — batch Ask on P0/P1 prompts; store runs with debug=true.
  2. Rank / prefer — humans mark better/worse (or pass vs fail) in manualEval; optionally pair two runs for the same prompt →
     (chosen, rejected).
  3. Bootstrap — use llmJudge + Recall@K to drop junk before humans; use idealResponse for supervised fine-tunes.
  4. Train — export pairs to DPO/RLHF trainer; keep Prompt Lab as the eval harness (same goldens, same judges) so policy
     updates don’t silently regress P0.

  Design rule that makes this work

  Independent scorers on durable runs — you can change the reward model or judge without losing history, and you never conflate
  “sounds good” (LLM) with “called the right tools” (routing) with “human preferred this” (manual). That’s exactly what you want
  before RLHF: clean, separable preference signals.

  One line: Prompt Lab = capture + label + score loop; RLHF = train on those labels — same artifacts, different consumer.

Fixes #5693

Problem

When using the non-streaming API (call()), the reasoningContent field was not included in the AssistantMessage metadata. However, the streaming API (stream()) correctly included it. This inconsistency affected models like DeepSeek-R1 and Qwen3.5-plus that return reasoning content in their API responses.

Root Cause

In OpenAiChatModel.java, the internalCall method built the metadata map without the reasoningContent field, while internalStream included it.

Solution

Added reasoningContent to the metadata map in the internalCall method to ensure consistency with the streaming API.

Added reasoningContent to metadata in internalCall
Added unit tests to verify behavior
