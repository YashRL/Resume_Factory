Read in details: BlendLXP Agentic Platform.md

### Ask Engine 3 / Capability-Based Tool Routing System — Summary

Designed and implemented a **capability-based multi-agent architecture** to address the latency problem created by traditional Agent-to-Agent execution, where an **Agent A** invoking Agents B and C caused each downstream agent to start its own independent **ReAct loop**, multiplying reasoning and tool-execution overhead. Instead of executing entire sub-agents, I introduced a **capability layer** in which the Ask Engine can request another agent’s **capabilities, prompts, tools, and output structure**, then execute that capability directly inside its **own ReAct loop**. I also introduced a dedicated **Agentic Router** to classify and route requests to specialized agents while keeping the Ask Engine as the primary low-latency orchestration layer. The architecture therefore combines **multi-agent specialization with capability-level reuse**, preserving agent-specific expertise without paying the latency cost of repeatedly spawning nested agent loops. The key engineering challenge was not achieving functional results or response quality, but **reducing orchestration latency without compromising quality**, which led to the capability-oriented design.

* **4 primary routed agents** implemented: **Ask, Pulse, Recommendations, and Finder**
* **1 central Agentic Router** handles intent classification and agent dispatch
* **64 live `@McpTool` capabilities** available through the shared MCP layer
* **50 tools** retrieved as the pre-rerank candidate set
* **20 tools** reduced to the final LLM allowlist before ReAct execution
* **2 specialized agents** — Pulse and Recommendations — expose reusable **capability cards**
* **Capability-level A2A** avoids executing an entire downstream ReAct agent when only its capabilities are required
* Capability contract exposes **prompts + tools + output structure**, allowing the Ask Engine to execute the capability in its own loop
* **1 ReAct loop** remains the primary execution context instead of nesting independent loops across agents
* **1 shared MCP capability layer** provides common data/tool access across agents
* **4-way intent routing:** `ask | pulse | recommendations | finder`
* Designed specifically to reduce **multi-agent orchestration latency** while maintaining response quality
* **Vector + BM25F/TF-IDF/RRF** tool routing used to reduce the effective tool search space before ReAct
* **Quality-first development** was a key engineering principle: establish correct results and architecture first, then optimize latency without sacrificing output quality
* Key architectural learning: **strong structure and clear capability boundaries enable faster optimization and development**


### Prompt Lab — BlendLXP AI Evaluation & Red-Teaming Platform — Summary

Built **Prompt Lab as a debugging, evaluation, and red-teaming infrastructure for the entire BlendLXP AI foundation**, rather than a conventional evaluation dashboard. The platform was created because once the agents were working, the major engineering problem became understanding **why they worked, where they failed, what they cost, how ReAct trajectories behaved, which tools/prompts/guardrails created bottlenecks, and how the system behaved across unknown edge cases**. I designed the architecture as a **run-centric control plane with separated execution and independent scorers**, where every Ask/Pulse execution is captured once as a durable run artifact and can then be analyzed through **LLM-as-Judge, deterministic tool-routing Recall@K, manual evaluation, ideal responses, trace analysis, replay, and batch evaluation** without one evaluation method overwriting another. I also extended the platform into an **agentic red-teaming system inspired by OpenAI's red-teaming competition and Netflix Chaos Monkey**, deliberately attempting to break agents and challenge their guardrails. A major part of the platform is the **Golden Set preparation loop**, where product experts can review generated responses, provide feedback, and iteratively produce ideal responses without requiring deep technical knowledge; these human preferences, ideal responses, trajectories, and evaluation signals can subsequently become a foundation for **SFT/DPO/RLHF-style training pipelines**. As the lead AI engineer on the project, I owned the architecture and implementation decisions end-to-end, effectively turning Prompt Lab into the **quality, debugging, experimentation, and future training-data layer around the agentic platform**.

* **1 unified Prompt Lab platform** covering evaluation, debugging, red-teaming, replay, and quality analysis
* **Run-centric architecture** — capture an agent execution once and score it through multiple independent evaluation systems
* **4 routed AI agents** currently exercised by the broader BlendLXP agentic platform
* **64+ live MCP tools** available for tool-routing and trajectory evaluation
* **Recall@5 tool-routing evaluation** used to measure whether the correct capabilities are retrieved
* **LLM-as-Judge** evaluates dimensions including **groundedness, tool routing, trajectory quality, actionability, relevance, and correctness**
* **0.75+** judge score treated as **Pass**, with **0.40+** treated as Partial
* **P0 → P1 → P2** Golden Set prioritization so critical product behaviors are evaluated before lower-priority edge cases
* **Batch evaluation** enables entire scenario packs to be executed and analyzed instead of manually checking responses one by one
* **Durable run artifacts** preserve prompts, responses, tool calls, widgets, traces, expected outputs, and evaluation metadata for replay and re-judging
* **Human-in-the-loop Golden Set creation** allows product experts to generate feedback and ideal responses without needing to understand the underlying agent implementation
* **Agentic red-teaming** designed to intentionally challenge agents, prompts, and guardrails rather than testing only expected happy paths
* **Chaos-Monkey-inspired philosophy** — deliberately introduce adversarial/edge-case challenges to discover weaknesses before users do
* **LLM Judge + deterministic evaluation + human evaluation** kept as separate signals so qualitative and quantitative failures remain distinguishable
* **Replay capability** allows the same historical execution to be evaluated again as prompts, judges, or models evolve
* **RLHF/DPO-ready data pipeline:** run artifacts → human preference → chosen/rejected responses → preference dataset
* **SFT-ready pipeline:** ideal responses from Golden Set preparation can become supervised training targets
* **10× faster personal QA/debugging workflow** by replacing manual response-by-response inspection with batch-level evaluation and automatically surfaced failure patterns
* **Product-team feedback loop:** generated response → human feedback → temporary ideal response → developer iteration → re-test → approved Golden Set
* **Designed as infrastructure, not merely an eval tool** — the same system supports **development, QA, regression testing, red-teaming, product validation, prompt optimization, model improvement, and future RLHF**
* **Core engineering principle:** **capture once → inspect many ways → improve → replay**, creating a persistent feedback loop between agents, developers, product experts, and future model training
  
  
  
### Enterprise Hierarchical RAG & EPO Knowledge Retrieval Platform — Summary

Built an **enterprise-grade hierarchical document intelligence and RAG platform for the European Patient Organisation (EPO)**, starting around **April 2025**, to solve a deceptively difficult requirement: users needed to search across **1,000+ books and large document collections** while receiving not just an answer, but the exact **book, author, chapter, heading, page, and paragraph context** behind the information. Instead of treating documents as flat text, I intuitively designed a **four-level hierarchical ingestion system** that extracts and stores **paragraph, page, chapter, and heading-level knowledge independently**, increasing the searchable representation by approximately **4×** while dramatically expanding the retrieval possibilities. The pipeline combined **GROBID, pdfplumber, PDF metadata/TOC extraction, Python document-processing libraries, and Tesseract OCR** to reconstruct document structure from heterogeneous PDFs, with **PostgreSQL/PGVector** powering semantic and hybrid retrieval. A major engineering challenge was deduplication and document versioning: I created a **paragraph-level signature mechanism** so the system could detect the same content even when a document was re-uploaded under a different filename or by another user, while version relationships allowed unchanged content to be reused and only new/changed content to be ingested. The platform also evolved beyond basic vector RAG with **keyword and graph-based relationships** to address retrieval bias caused by larger documents and overlapping content. The resulting system was used by **EPO** and demonstrated the ability to handle **1,000+ books and large-scale document testing** while preserving highly precise document provenance; the architecture was also designed with a future path toward **vision-language models and vision embeddings** for diagrams, images, and visual document intelligence.

* **1,000+ books** supported in the enterprise document corpus
* Built for the **European Patient Organisation (EPO)** as a real-world knowledge retrieval system
* **4-level hierarchical ingestion:** paragraphs → pages → chapters → headings
* Approximately **4× searchable representation/storage footprint** created intentionally to support multi-level retrieval
* Search can leverage **book, author, chapter, heading, page, paragraph, and semantic content** as retrieval context
* **PGVector + PostgreSQL** used for semantic/vector retrieval and document metadata
* **Hybrid retrieval architecture** combining semantic search with keyword/graph relationships
* **GROBID** used for structured PDF/document extraction
* **pdfplumber** used for faster extraction and modern PDF structures such as **TOCs and embedded metadata**
* **Tesseract OCR** incorporated for image/text extraction from PDFs
* **Paragraph-level signatures** created to detect duplicate knowledge across different documents, filenames, users, and re-ingestions
* **Version-aware ingestion:** unchanged content is reused while only new/changed content requires ingestion
* **Non-destructive deletion/version unlinking:** deleting one document version does not unnecessarily remove shared knowledge used by other versions
* **4× storage challenge** directly drove the deduplication and version-management architecture
* **Graph + keyword relationships** introduced to reduce retrieval bias toward larger documents and overlapping text
* Provenance-aware results designed to return **book → author → chapter → page → paragraph** context rather than an opaque generated answer
* **Multi-format / heterogeneous PDF ingestion** designed around real enterprise document variability
* Architecture designed for **agent integration**, allowing an AI agent to search different hierarchy levels depending on the user's question
* Future-ready extension identified for **Vision LLM + vision embedding models** to understand and retrieve diagrams, figures, and images alongside text
* **Production-used EPO system**, validated against a large volume of real-world documents
* **End-to-end ownership:** requirements understanding → document extraction → hierarchical representation → deduplication → versioning → retrieval → APIs → testing
* First major **end-to-end project independently engineered**, providing experience across real requirements gathering, consultant/customer interaction, architecture, implementation, and enterprise delivery






### MCP Research & Implementation — Summary

Explored **Model Context Protocol (MCP) from its early emergence through practical implementation**, moving beyond simply consuming MCP tools to understanding the underlying architecture, security model, clients, servers, SDKs, and production deployment considerations. My starting point was traditional **LLM function/tool calling**, where I recognized that much of the intuition behind MCP was familiar—LLMs inspect tool descriptions/docstrings and decide which functions to invoke—but MCP introduced a standardized protocol layer around these capabilities using **JSON-RPC 2.0**, structured tool discovery, resources, prompts, and decorators such as `@McpTool`. I experimented with **FastMCP, MCP SDKs, MCP clients and servers**, explored deployment challenges including **Cloud Foundry**, and later incorporated MCP into larger agentic architectures, including experiments where **agents themselves exposed MCP-like capabilities**, eventually contributing to A2A-style agent communication patterns. One of the most valuable areas of the research was MCP security: unlike conventional backend systems where **JWT-based identity propagation** is common, MCP creates interesting questions around securely passing sensitive context such as user IDs and personal information to remote tools. I developed a **secret-reference/token approach**—later recognizing the broader pattern as a *phantom token* technique—where the client sends a non-sensitive secret identifier and the MCP server resolves the actual user context internally, while also investigating **backend-issued JWT propagation and API-token authentication** as alternative security models. This research became foundational knowledge that I subsequently applied when designing MCP-based production agent architectures.

* **1 major protocol ecosystem** explored: **Model Context Protocol (MCP)**
* **JSON-RPC 2.0** identified as the underlying communication foundation
* **3+ implementation approaches** explored: **FastMCP, MCP SDK, custom MCP server/client implementations**
* Investigated both **MCP clients + MCP servers** rather than only consuming existing tools
* Explored **tool discovery, function descriptions/docstrings, decorators, prompts, and structured tool schemas**
* Compared traditional **LLM function calling → standardized MCP tool ecosystem**
* Investigated **production deployment**, including **Cloud Foundry deployment constraints**
* Designed and experimented with **secure user-context propagation** without directly exposing sensitive user data to the client
* Explored the **phantom-token pattern:** opaque secret/reference → server-side resolution of protected user context
* Evaluated **JWT propagation** as a backend-controlled MCP authentication approach
* Evaluated **API-token authentication** as a simpler MCP server security mechanism
* Identified **identity/context propagation** as one of the key architectural challenges in MCP-based enterprise systems
* Later reused MCP concepts to build **agent-as-capability experiments** and A2A-like communication patterns
* Research directly influenced later **production agentic architectures using MCP as the capability/data layer**
* Built this understanding during the **early adoption phase of MCP**, when the ecosystem and implementation patterns were still rapidly evolving
* Key learning: MCP is not simply "LLM tool calling"—it provides a **standardized protocol and capability ecosystem around tool discovery, invocation, context, and interoperability**

### TalentBot — Memory, Personalization & Context Architecture

Designed a multi-layer **agent memory system** so TalentBot could maintain useful conversational context without continuously sending the entire conversation back to the model. The implementation explored **ICM (Indexed Context Memory)** and its episodic-decay and typed-relation-graph approach, combined with a custom multi-step memory strategy consisting of **session memory, short-term conversational memory, long-term semantic memory, session summaries and document-aware RAG context**. Recent interactions could be retained directly, while older conversations were progressively summarized or selected according to their relevance to the current query. When a user attached a document, the relevant document metadata and RAG context could also participate in the agent's contextual reasoning. This created a practical memory hierarchy where the agent could distinguish between **what was just discussed, what mattered from the broader session, what should be remembered long-term, and what information belonged to an attached knowledge source**, giving the conversational system substantially more usable context without treating the entire conversation as one massive prompt.

* **5+ contextual layers** explored across session, short-term, long-term, summary and document/RAG memory
* **Last ~3 responses** retained as direct short-term conversational context
* **Last ~10 responses** incorporated into longer-term contextual processing
* Older context **truncated/summarized based on semantic relevance**
* Up to approximately **1M-token context boundary** explored for long-term contextual retrieval
* **ICM / Indexed Context Memory** explored for episodic and relationship-based memory
* **Typed relation graph** used to represent relationships between remembered information
* **Session summaries** generated to preserve important historical context compactly
* **Document-aware memory** connected attached-document metadata with RAG retrieval
* Memory designed around **relevance rather than blindly replaying conversation history**

### PII Detection & Redaction

Developed the **machine-learning pipeline for multilingual PII detection and redaction** to protect sensitive information flowing through the TalentBot ecosystem. The initial approach used **Microsoft Presidio** with a SpaCy NER model, but because the standard English-oriented entity recognition models were not sufficient for the project's multilingual requirements—particularly **Indian names**—I researched and extended the NER pipeline using domain-specific datasets and fine-tuning. The system was designed around **BIO/token-classification labeling** for entities such as `PERSON`, `LOCATION` and `ORGANIZATION`, with training data sourced from **AI4Bharat Naamapadam for Indian entities, WikiNER French for French, and CoNLL-2002 Spanish for Spanish**. The resulting approach allowed the redaction layer to recognize multilingual personal and organizational entities before sensitive information reached downstream AI components, while remaining compatible with the broader Presidio-based PII protection architecture.

### Brain — Master Agent / Agent Harness

Built **Brain, a Master Agent / Agent Harness from scratch using Java 17 and Spring Boot**, designed as a vendor-agnostic runtime for executing complex agentic workflows rather than as a single-purpose chatbot. The system implements an explicit **Planner → ReAct Runtime → Tool Execution → Observation → Synthesis** lifecycle, allowing an agent to dynamically reason over a task, select relevant capabilities, execute tools, observe their results, recover from failures, and produce a final response. The framework supports multiple execution mechanisms including **MCP servers, A2A agents, n8n workflows, native tools, and JSON-RPC 2.0**, while a unified `LLMProvider` abstraction allows different model providers to be integrated without coupling the core runtime to a specific vendor. The architecture was intentionally built around composable capabilities, allowing tools, models, agents, and external execution systems to act as interchangeable building blocks.

A major focus of the implementation was making agent execution reliable and scalable beyond a basic tool-calling loop. Brain dynamically selects a tactical subset of relevant tools instead of exposing the entire tool catalog to the LLM, using **intent-based orchestration and pgvector semantic tool search** when required. It includes **Smart Parameter Resolution** for recovering missing or malformed tool arguments, **Adaptive Tool Memory** for learning from previous tool-call failures and successes, search-specific **circuit breakers and deduplication**, MCP session rediscovery, retry mechanisms, and runtime identity/context injection. Complex tasks can be delegated through a `delegate_task` mechanism that creates isolated child agent runtimes with their own ReAct context and constrained execution budgets. An **Observer Agent** evaluates intermediate observations and provides guidance to the runtime, while the Planner determines execution modes and step budgets for short, medium, and long-running tasks.

The harness was also designed as an **enterprise-oriented integration layer**, supporting REST, SSE streaming, WebSockets, Microsoft Teams/Bot Framework integration, and JSON-RPC 2.0 endpoints. It abstracts differences between model providers such as **OpenAI, NVIDIA, and SAP AI Core**, while providing a dynamic registry for MCP servers and their tools. PostgreSQL is used for tool catalogs, user MCP configuration, session state, and semantic tool discovery. The system also incorporates operational considerations such as asynchronous Teams execution, context pruning, request tracking, timeout handling, deterministic automation fallbacks, and multi-tenant tool visibility. Brain ultimately became the foundational agent runtime that could be composed into larger agentic systems, but the **Agent Harness itself was developed as an independent piece of AI infrastructure for orchestrating models, tools, and agents through a common execution framework.**

* **Java 17 + Spring Boot** agent runtime built from scratch
* Explicit **Planner → ReAct → Tool → Observation → Synthesis** execution lifecycle
* **Master Agent** capable of delegating complex tasks to isolated sub-agents
* **3 planning modes:** SHORT, MID and LONG with execution budgets
* Dynamic tactical tool selection, typically exposing only **3–7 relevant tools** to the LLM
* Semantic tool discovery using **PostgreSQL + pgvector**
* **MCP, A2A, n8n, Native Tools and JSON-RPC 2.0** execution support
* Multi-provider LLM abstraction supporting **OpenAI, NVIDIA and SAP AI Core**
* **Smart Parameter Resolver** for recovering missing and malformed tool arguments
* **Adaptive Tool Memory** for learning from tool execution failures and successes
* **Observer Agent** for intermediate-result reflection and execution guidance
* Search **circuit breakers** to prevent repetitive or infinite search loops
* Tool-call **deduplication and retry mechanisms**
* MCP connection/session rediscovery following transport failures
* Parent/child **agent context isolation and memory synchronization**
* REST, **SSE streaming and WebSocket** execution interfaces
* **Microsoft Teams / Bot Framework** integration with asynchronous execution
* Multi-tenant MCP/tool visibility and user-specific capability controls
* PostgreSQL-backed **tool registry, session memory and configuration**
* Dynamic prompt construction to reduce **context-window and token bloat**
* Deterministic automation fallback for predefined execution sequences
* Designed as a **composable agent infrastructure layer**, rather than a single-purpose AI application



### Agentic AI Marketplace — Enterprise Agent Platform

Worked on an **enterprise Agentic AI Marketplace**, an extensible platform designed to bring different AI agents, tools, models, workflows, and AI capabilities into a single ecosystem. Rather than building another standalone chatbot, the platform was designed around the idea that **agents and AI capabilities should behave like composable building blocks**: users could discover, enable, configure, and eventually publish agents and external capabilities through a centralized marketplace. The platform incorporated the **Brain Master Agent / Agent Harness** as its core execution infrastructure, while extending beyond the runtime into agent discovery, integrations, memory, PII protection, scheduling, enterprise systems, and external agent ecosystems. Agents could communicate through mechanisms such as **MCP and A2A**, while workflow-based systems such as **n8n** could also participate as executable capabilities. The architecture was intentionally model-agnostic, treating LLMs and other AI systems as interchangeable providers so that the platform could evolve beyond a single model or even beyond LLMs toward **ASR, TTS, NER, vision, and other AI workloads**.

The platform brought together multiple specialized components and agentic applications. **TalentBot** was extended as an agent within the ecosystem, combining enterprise RAG, document intelligence, SuccessFactors capabilities, Blend and Blend Courses agents, question-paper generation, conversational memory, and PII protection. The architecture also supported specialized agents that could operate independently or be orchestrated by the Master Agent, allowing complex problems to be decomposed into smaller tasks and delegated to agents with their own context and capabilities. A dedicated **tool-routing layer** allowed large tool ecosystems to be dynamically discovered and selected, while an **Observer mechanism** could operate alongside agent execution to monitor progress, reduce unnecessary execution and token consumption, and provide additional guidance. Prompt chains were also treated as reusable capabilities, allowing large system instructions to be decomposed into dynamically invoked prompt components rather than continuously bloating the agent context.

A complete **AI capability platform** surrounded the agent runtime. The system incorporated a reusable **multilingual PII detection and redaction layer**, enterprise **memory infrastructure**, MCP and A2A connectivity, workflow execution, scheduling and triggers for proactive agents, and integrations with enterprise communication platforms such as **Microsoft Teams / Bot Framework**. The scheduling layer was intended to allow agents to execute proactively based on triggers or schedules rather than only responding to user requests. The marketplace experience provided a central interface for discovering and enabling capabilities, with the architectural direction allowing users to eventually publish their own **MCP servers, A2A agents, workflows, and other capabilities**. A longer-term direction for the platform was a **low-code agent creation system** in which a user could describe a desired capability in natural language, have the platform select and compose the required models, tools, prompts, agents, data sources, and workflows, and generate a deployable agent through standardized contracts such as **JSON-RPC 2.0**. The same abstraction was envisioned to support deployment across different environments and programming ecosystems, making the Marketplace less of an application and more of an **AI capability platform for composing, deploying, and connecting enterprise agents**.

### AI Agent Security Red Team — OpenAI/Kaggle Competition — Summary

Participated in the **latest OpenAI/Kaggle AI Agent Security Red-Team competition**, focusing on a deeper question than whether an LLM can be "jailbroken": **how robust are the guardrails surrounding an agent when the model is given instructions that appear legitimate but cause its tools to perform harmful actions?** Through source-code and guardrail analysis, I identified a key attack surface in agentic systems where the LLM itself may faithfully execute a seemingly valid tool call because its training does not inherently teach it to question every tool instruction; instead, security often depends on an **observer/guardrail layer monitoring tool calls and blocking suspicious behavior**. I therefore built an automated red-team agent that iteratively generated and optimized adversarial prompts, analyzed which guardrail predicates were being triggered, and refined attacks until they could bypass the detected rule patterns while still producing the intended tool behavior. The experimentation covered **prompt injection, confused-deputy behavior, tool-call vulnerabilities, multi-predicate attacks, guardrail analysis, source-code auditing, automated candidate generation, and attack optimization**, ultimately reaching **Level-5 severity across 2,000 test cases spanning 4 query categories**. The project gave me hands-on experience thinking about AI agents as **security-sensitive software systems**, where the attack surface extends beyond the model into tools, permissions, routing, observation layers, and deterministic guardrails.

* **2,000+** adversarial test cases evaluated
* **4** distinct query/attack categories covered
* **Level-5 severity** reached through optimized attack cases
* Built a **custom automated red-team agent** for candidate generation and attack optimization
* Implemented an iterative **generate → test → observe guardrail → optimize → retest** attack loop
* Investigated **prompt injection** against agentic workflows
* Analyzed **tool-call vulnerabilities** where seemingly valid instructions could trigger sensitive operations
* Investigated **confused-deputy** behavior in tool-enabled agents
* Tested **multi-predicate attacks** designed to evade rule combinations rather than a single guardrail
* Performed **source-code auditing** of agent/guardrail behavior to understand the actual security boundary
* Studied **observer-based guardrails** that monitor tool calls and terminate execution when suspicious patterns are detected
* Demonstrated that agent security is not solely a model-alignment problem — **tools, permissions, guardrails, and execution policies form a critical part of the security boundary**
* Built attack optimization around **guardrail feedback**, rather than relying on manually crafted jailbreak prompts

## Internet Search & Web Content Extraction API

Built a **lightweight, asynchronous web search and content-extraction API in late 2024** as an early retrieval infrastructure project for AI systems. The service was implemented using **FastAPI** and combined DuckDuckGo search with **BM25 relevance reranking**, allowing search results to be fetched, crawled, scored, and returned as structured results rather than simply passing raw search-engine responses downstream. The API supported multiple search modalities including **text, images, videos, and news**, with configurable regional, temporal, SafeSearch, and media-specific filters. For text search, results were fetched concurrently using asynchronous HTTP clients, duplicate URLs were removed, page content was extracted, and BM25 was applied to rank results according to their relevance to the original query. This project became an early foundation for thinking about **search as an AI capability/tool**, rather than simply an external API call.

The second major component was a **layered web-content extraction pipeline** designed to deal with the extremely inconsistent nature of modern websites. The extractor first attempted high-quality article extraction using **Trafilatura**, then fell back to **BeautifulSoup** for conventional HTML pages, and finally used **headless Selenium/Chrome** to render JavaScript-heavy Single Page Applications when static extraction failed. YouTube URLs were handled through a dedicated transcript extraction path, allowing video content to become machine-readable text as well. The service also incorporated **SSRF protection** on the extraction endpoint by blocking localhost, internal addresses, and loopback subnets. This made the project more than a simple search wrapper: it became a small **retrieval + crawling + content normalization service** capable of turning heterogeneous web resources into structured information suitable for downstream AI and RAG systems.
